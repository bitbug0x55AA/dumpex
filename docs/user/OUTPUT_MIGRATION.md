# Output Schema Migration

This document records dumpex's structured-output compatibility history. It is
for consumers validating archived case records or upgrading parsers. For the
current contract, see [Output and Evidence Schema](OUTPUT_SCHEMA.md).

## Compatibility rule

Select a schema from the document's own `meta.schema_version`; never rewrite an
archived result merely to make it validate against a newer schema. Historical
schema files remain packaged and frozen so old evidence can still be validated.

A new schema version is required when dumpex changes the produced wire shape in
a way an existing consumer must understand, including:

- adding a `result.kind` value;
- adding/removing a required field on a closed object;
- changing a closed enum;
- removing or reshaping a field producers emitted;
- changing a record's keying or nesting.

Clarifying documentation, console-only presentation, or adding a coverage code
to an intentionally open string vocabulary does not by itself require a bump.

## Version summary

| Version | Consumer-visible change |
|---|---|
| 2.20 | Widened `anchor_pe_context.classification`'s "no module owns this" bucket from two values to five, split by the captured region's own CONFIRMED type -- and, for MEM_IMAGE, the CONFIRMED registration state -- rather than collapsed into one bucket: `private` (confirmed MEM_PRIVATE) and `unresolved` (no module AND no region place the anchor) keep their v2.18 meanings; the prior blanket case is now `mapped` (confirmed MEM_MAPPED, e.g. a resource-only file view), `unregistered_image` (confirmed MEM_IMAGE AND a module list confirmed no module covers this address -- a manually mapped or stomped module, the most suspicious of the five), `image_registration_unavailable` (confirmed MEM_IMAGE, but no module list was available to check registration at all -- a different gap from confirmed-unregistered: asserting `unregistered_image` here would claim a module list was consulted and came back negative when none was ever consulted), or `region_type_unavailable` (the region's own type is `null` or an unrecognized/numeric value -- a genuine gap, never asserted as `mapped`). Module absence alone never implies private memory, and a MEM_IMAGE region's registration is never assumed confirmed-unregistered just because it isn't confirmed registered. `--hunt hollowing`'s `hollowingDetails` gains `region_type`: the image-base region's own OBSERVED MemoryInfo type (e.g. `MEM_PRIVATE` or `MEM_MAPPED`), null exactly when `mem_private_at_base` is (the region wasn't found at all). `mem_private_at_base` itself is unchanged, but its name is now documented precisely: it is true for ANY non-MEM_IMAGE type at the image base, not MEM_PRIVATE specifically -- `region_type` is where a consumer reads which type it actually was. The hollowing hunter's structural-correlation `inference`/`rationale` and console verdict/Score text likewise name the OBSERVED type rather than asserting MEM_PRIVATE for a MEM_MAPPED image base. `reportSummary` gains `hits_mapped`, `hits_unregistered_image`, `hits_image_registration_unavailable`, and `hits_region_type_unavailable`, all `integer`/`null` (null outside `--report-string` mode, the same shape `hits_private`/`hits_image` already use): the existing `hits_private` counter is grouping/actionability shorthand (every hit NOT attributed to a resolved image module), not a memory-type claim, and already folded MEM_MAPPED, MEM_IMAGE, and unresolvable-type hits in alongside genuine MEM_PRIVATE ones; the four new counters mirror `anchorPeContext.classification`'s own five-way "no module owns this" split exactly -- `hits_unregistered_image` (a module list CONFIRMED no module covers the address) is kept distinct from `hits_image_registration_unavailable` (no module list was available to check at all, a strictly weaker fact) the same way the classification values are, and `hits_region_type_unavailable` covers a `null`/unrecognized region type -- so a summary-only consumer can tell them apart without reading every card and `hits_private` minus all four is genuine, confirmed MEM_PRIVATE, never a remainder that silently absorbs an unresolved type or unresolved registration state; `card_count`/`hits_sharing_a_region`/`hits_skipped_for_budget`'s existing relationship to `hits_private` is unchanged. `reportRegionInfo` gains `pe_header_state`: `ok` / `pe_invalid` / `short_read` (the same vocabulary `dumpex.commands.process`'s main-image classification uses), the structural-validity fact `has_injected_pe`'s own derivation rests on, set exactly when `mz_header_detected` is true and `module_context` is confirmed `unregistered` (the only case a structural PE parse is ever attempted) and `null` otherwise. It is enforced bidirectionally against `has_injected_pe`: `short_read` forces `has_injected_pe` to `null` (a capture-length gap, not a rejection), and `ok` forces `has_injected_pe` to equal (MEM_PRIVATE or executable) exactly -- a schema-level `allOf` conditional, not just Python, rejects both a fabricated finding and a dropped one. `--report`'s v2.17/v2.18/v2.19 `process_enrichment`, `exception_context`, `allocation_neighborhood`, `handle_correlation`, `string_context`, `pe_context`, `anchor_pe_context`, `instruction_context` and `iat_correlation` projections, and their `missing` / `partial` / `complete` evidence states, are carried forward unchanged. Unlike most Producer-behavior-only releases, this one DOES move `coverage.status` and the exit code for a real (if narrow) set of documents: a `--report` triage card whose target region was read in full but whose PE header parse could not structurally settle `has_injected_pe` (`pe_header_state == "short_read"`) now reports `coverage.status: partial` via the new `REPORT_PE_HEADER_VALIDATION_INCOMPLETE` limitation, moving that run's exit code from 0 to 3 where it previously reported `complete`/0; a `--extract` run whose MZ-detected bytes need module/memory-type context that a missing `ModuleListStream`/`MemoryInfoListStream` cannot supply similarly reports `partial`/3 via the new `EXTRACT_MODULE_CONTEXT_UNAVAILABLE`/`EXTRACT_MEMORY_INFO_UNAVAILABLE` limitations, and one whose structural PE parse could not settle the question (`pe_header_state == "short_read"`) reports `partial`/3 via the new `EXTRACT_PE_HEADER_VALIDATION_INCOMPLETE` (see the Producer-behavior section below for all three). `verdict`/`findings` move only in the direction this whole version corrects: an MZ-only or unconfirmed candidate that previously scored `injected_pe` no longer does -- no verdict is ever newly promoted toward malicious by this version. Score, confidence, and Finding identity are otherwise unaffected, and the classification/`region_type`/`pe_header_state` additions above need no schema-defined field to move on their own -- see the rows below. Later same-version addition (still schema_version 2.20, which is unreleased): `threadRecord` (`--threads`) and `reportThreadInfo` (`--report`'s anchor thread, Section 1, and any other thread admitted into Section 3 -- see below) gain `ip`/`ip_reg`: this thread's OWN live RIP/EIP, captured from its own CONTEXT/WOW64_CONTEXT at dump time, in the same both-or-neither shape `huntThreadRef` already used (`ip`/`ip_reg` are `null` together, or both set). `start_address` (where the thread BEGAN) and `ip` (where it IS captured executing right now) are independent facts from independent sources: neither field is derived from or substitutes for the other, and a thread whose current `ip` differs from its own `start_address` retains both addresses, each with its own availability. `ip`/`ip_reg` are `null` together whenever this thread's CONTEXT was not captured or could not be parsed for it -- get_thread_contexts' own "not in this list" contract -- and are never defaulted to that thread's `start_address` or to 0. A genuinely-zero CONTEXT (real captured data) is never annotated on the console as a confirmed divergent location, matching the instruction-anchor candidates' own `addr > 0` usability rule; `--threads` extends the same treatment to a thread whose ThreadInfoListStream record flags its own context as invalid (`DumpFlags == MINIDUMP_THREAD_INFO_INVALID_CONTEXT`) when a base-stream CONTEXT parsed anyway, from the record's own raw `DumpFlags` bit mask, so a genuinely combined flag value carrying that bit is caught exactly like a lone one. `reportThreadInfo` also gains `region_membership` (`start` / `current` / `start_and_current` / `null`, Section 3 only -- always `null` on Section 1's own anchor-thread entry): which address actually placed a Section 3 entry in the list, published on the record itself rather than recomputed independently at render time, so console and JSON can never disagree about it. `backing_module`/`module_context` always describe `start_address` specifically, never `ip`, on every entry regardless of `region_membership` -- the console names this explicitly so a `current`-only entry's module attribution is never mistaken for describing the region it is listed for. `module_context: null` (start address itself unrecorded) is now told apart on the console from MODULE_CONTEXT_UNAVAILABLE (ModuleListStream itself missing) in Section 3 the same way Section 1 already did -- the two are different gaps and were being conflated into the same "module classification unavailable" text. A `start_address` that was genuinely never recorded stays `null` rather than being coerced to `0x0` (which previously let a missing value resolve through module lookup as a confirmed "not in any module" finding); `--report`'s TID resolution now consults the base ThreadListStream as well as ThreadInfoListStream, so a TID present only in the former (its `CurrentIP` fully available, its `start_address` genuinely unknown) no longer reports "TID not found in dump" -- and, when that TID's own current IP is a usable (non-zero) address, it is now the card's own anchor, so the card actually examines that region instead of resolving none at all while still reporting a verdict. `--report`'s per-card `coverage.sources` additionally attributes the base ThreadListStream by name (`threads`); unlike `thread_info`, its absence alone does not move `coverage.status`/exit code. `--report`'s console Section 3 is corrected from "THREADS EXECUTING IN THIS REGION" to a header naming both facts it uses: membership is now by a thread's recorded `start_address` OR its captured current IP falling inside the region (reusing the identical region-bounds check already used for `start_address` -- no new algorithm), and each console line names which fact(s) placed that thread there; `unbacked_thread` is still derived only from a thread's own `start_address` failing module resolution, unchanged from before this addition -- a thread admitted only by its current IP never contributes a new finding. A `--report-tid` card whose anchor thread has no usable current IP examined (unavailable, zero, or outside the region the card actually resolved -- including a card that resolved no region at all) now carries a `REPORT_CURRENT_IP_NOT_EXAMINED` diagnostic and an explicit `Scope:` line beside the ASSESSMENT verdict, worded for which of those cases applies. No new correlation, stack-scanning, or disassembly algorithm is added anywhere in this addition: it is a labeling and evidence-retention fix, not a new detection signal, and `findings`/`verdict` keep their existing four-key vocabulary. Unlike every other field and diagnostic addition in this row, the base-only-TID anchor fallback described above genuinely reads a region it previously left unexamined, so it is the one exception to a purely-labeling change: `coverage.status` and the exit code DO move for that narrow, base-only-TID-with-usable-current-IP set of documents whenever the newly-examined region itself carries an evidence gap (e.g. a short/truncated read), the same way the PE-header `short_read` case earlier in this row does; `findings`/`verdict` can likewise move for that same narrow set (a card that previously resolved no anchor and reported `CLEAN` over zero evidence can now report a real finding and a higher verdict for the region its own current IP names) -- this is the fix AC1's own inverse gap required, not a new detection signal, and it is bounded to cards whose thread has no recorded start address at all. Every OTHER field and diagnostic addition in this row (`ip`/`ip_reg`, `region_membership`, the TID-resolution fix itself, `REPORT_CURRENT_IP_NOT_EXAMINED`, and the Scope-text corrections below) is labeling/evidence-retention only and does not move `coverage.status`, the exit code, `findings`, or `verdict`. This fallback is also labeled on the wire: a base-only-TID fallback card gets its own `anchor_source` value, `tid_current_ip`, distinct from the ordinary `tid` value an anchor with a recorded start address uses, and the console names the resolved address and its source under `TID` in that case. `reportThreadInfo` also gains `ip_context_conflict`: true exactly when `ip` is set AND this TID's own ThreadInfoListStream record independently flags that same context as invalid (DumpFlags == MINIDUMP_THREAD_INFO_INVALID_CONTEXT, the same tag `--threads` renders as `[NO_CTX]`) -- a genuine disagreement between the dump's two thread sources. `ip` keeps the real, parsed value either way; the conflict travels with it to console, JSON, and the Scope note, which now fires for a conflicted value regardless of whether it falls inside the region this card examined -- `region_membership` itself carries no disputed variant (it says WHICH address admitted a Section 3 entry, never whether that address is trustworthy); a consumer that needs both facts together must separately check `ip_context_conflict` (ANDing the two fields). The Scope note's own "this assessment covers ... recorded start address only" claim is no longer asserted unconditionally when the current IP is unusable: it is true only when the region this card actually resolved covers that start address, which is not guaranteed when an independently supplied --report-addr chose a different region -- the note then names the region actually examined instead. The classification also collapsed two different states into one "could not be determined" wording -- no CONTEXT was ever captured for this TID at all, versus a CONTEXT WAS captured and genuinely holds 0 -- both the Scope note and the `REPORT_CURRENT_IP_NOT_EXAMINED` diagnostic now distinguish them across all four region shapes, and the conflicted-value check fires for a captured 0 exactly as it does for any other captured value, so a genuinely disputed-and-zero context is never reported as merely zero. `reportThreadInfo.region_membership` is now enforced bidirectionally by the schema, not just documented: `null` on Section 1's own anchor-thread entry and one of `start`/`current`/`start_and_current` on every Section 3 `other_threads_in_region` entry, in both directions. `threadRecord` (`--threads`) gains the identical `ip_context_conflict` field, computed the same way `reportThreadInfo`'s is, so `--threads` and `--report` now publish this fact in the same schema-validated shape for the same TID rather than one side deriving it at render time from the free-form `flags` list alone. `ip_context_conflict` (on `reportThreadInfo`, `threadRecord`, and now `huntThreadRef` -- see below) was a plain boolean, unable to distinguish a real ThreadInfoListStream record confirming no dispute from a TID with no such record to check at all -- the field is now tri-state: `true`/`false` when a real record's readable `DumpFlags` settle the question, `null` when no `DumpFlags` value could be established for this TID at all -- no ThreadInfoListStream record, or a record whose flags could not be read (always `false`, never `null`, when `ip` itself is `null`). The derivation moved to a single shared `dumpex.core.memory.ip_context_conflict_for`, consumed by `--threads`, `--report`, and `--hunt injection` alike. `--threads`' own coverage limitation for an absent or per-TID-mismatched ThreadInfoListStream now names `DumpFlags` among the unavailable fields, so a degraded dump's `false`-looking gap is machine-traceable to "undeterminable," not silently indistinguishable from a genuinely clean one. `huntThreadRef` (the `--hunt injection` wire shape for a thread reference) gains the identical tri-state `ip_context_conflict`, and a rip-correlated thread's `HuntThreadRef` no longer drops that thread's own recorded `start_address` (previously always `null` for a rip hit even when a real ThreadInfoListStream entry recorded one). `injection.allocation_correlation`'s `limitations` now name any contributing thread whose context is disputed or undeterminable, so the "currently execute inside" claim reads consistently with the identical fact `--threads`/`--report` already qualify for the same TID and dump -- this changes no score, confidence, or verdict, only which existing claim gets an explicit caveat. The join moved to a new shared `dumpex.core.memory.enriched_thread_contexts` (get_thread_contexts()'s own dicts, each augmented with this TID's `start_address`/`ip_context_conflict`), and `--hunt stomping` and `--hunt pipe` are now wired to it too -- `stomping.rip_in_anomalous_section_lead`, `stomping.verified_content_change` (that hunter's ONLY scored signal; a disputed or undeterminable RIP inside a changed range previously took confidence straight to HIGH and score straight to 2/2 with no qualification anywhere), and `pipe.corroboration` (whose `full_corroboration`/HIGH-confidence path is that hunter's own score=3 case) all now carry the identical leading `limitations` sentence via a new shared `dumpex.hunt._finding.disputed_conflict_limitation`. None of this moves any hunter's score or confidence -- only `limitations` gains the caveat. `--hunt cs_beacon` remains out of scope: it does not project a thread reference into any scored check's evidence the way injection/stomping/pipe do. (None of pipe's own internal `ip_context_conflict` tracking is projected into its existing wire shape -- `pipeDetails` is schema-unchanged by this addition; only `findings[].limitations` text carries it there. Stomping's own `stompingDetails.verified_changes[]` entries do carry it, from a later same-version addition described below.) Two structural-safety fixes ride along: `ThreadContext`/`RipHitEvidence.ip_context_conflict` now default to `None` (undeterminable) rather than `False` (confirmed clean) -- an omitted value now degrades to "cannot confirm" instead of granting an unearned confirmed-clean by omission; and `InjectionEvidence`'s rip-hits-match-thread-contexts invariant now also keys on `start_address`/`ip_context_conflict` (previously only `thread_id`/`ip`/`ip_reg`), so a rip hit whose dispute status silently disagrees with its own source `ThreadContext` is rejected at construction. Later same-version addition (still schema_version 2.20, unreleased): `stompingDetails.verified_changes[]` entries gain `rip_context_conflict`, the tri-state value that already qualified that same entry's `rip_in_changed_range` internally and already drove `stomping.verified_content_change`'s `limitations` caveat -- previously the only hunter where a disputed/undeterminable RIP moves a score published that score's own input with no structured field naming it as disputed, unlike `huntThreadRef.ip_context_conflict` for the equivalent per-thread fact on `--hunt injection`. Only meaningful (non-`false`) when `rip_in_changed_range` is `true`. `--threads` and `--report` now call `enriched_thread_contexts` directly instead of independently re-deriving the identical join from `get_thread_contexts` and `ip_context_conflict_for`, so that helper's own docstring claim of being the one join every command and hunter shares is accurate rather than aspirational; this is an internal-derivation change only and moves no field, score, confidence, verdict, or coverage.status. Later same-version addition (still schema_version 2.20, unreleased): `threadRecord` and `reportThreadInfo` gain `start_address_state` (`recorded`/`invalid`/`unverified`/`absent`) and `dump_flags_state` (`resolved`/`unresolved`/`absent`), enforced against each other and against `start_address` by a schema-level `allOf` conditional as well as in Python. A `start_address` of `null` had two very different causes a consumer could not tell apart: ThreadInfoListStream never covered this TID (`absent`), or it did and that record's own `DumpFlags` carry `MINIDUMP_THREAD_INFO_ERROR_THREAD`/`MINIDUMP_THREAD_INFO_INVALID_INFO`, which Windows documents as "no thread information exists beyond the thread identifier" (`invalid`). dumpex previously read such a record's `StartAddress` field as a real address, so the zero bytes the producer never wrote resolved through module lookup as a confirmed "not in any module" answer and manufactured an `unbacked_thread` finding, a `SUSPICIOUS` verdict, and (in `--report`) suppression of the current-IP anchor fallback out of missing evidence; that record's `start_address` is now `null`/`invalid`, its `module_context` `null`, its `create_time`/`exit_time`/`exit_status`/`kernel_time_100ns`/`user_time_100ns` `null`, and `--hunt injection`'s unbacked-thread scan skips it. `unverified` is the third cause: a real record whose `DumpFlags` value could not be established at all, whose `start_address` keeps its recorded value but never feeds a confirmed finding. `dump_flags_state` answers the companion question for `threadRecord.flags`: whether an empty list means "no flag set" (`resolved`) or "nothing is known" (`unresolved`). Both distinctions exist because dumpex no longer reads `DumpFlags` through the upstream `minidump` library's single-member `DumpFlags(value)` Enum lookup alone, which leaves the field unset for `0x00000000` AND for any combination (e.g. `INVALID_CONTEXT | EXITED_THREAD`, which `MiniDumpWriteDump` emits routinely) -- two states whose consequences are opposite. Each entry's raw `DumpFlags` UINT32 is now recovered from the stream's own bytes, so `threadRecord.flags` carries one tag per bit actually set rather than at most one tag in total, a combined value disputes a captured CONTEXT exactly as a lone `INVALID_CONTEXT` does, `0x0` stays a CONFIRMED absence of flags, and a value neither source establishes degrades to `unresolved`/`null` rather than to a confirmed clean answer. `huntThreadRef` keeps its existing field set; its `start_address` and tri-state `ip_context_conflict` carry the wider causes described here. `coverage.status` and the exit code do not move for any of this, and `findings`/`verdict` move only in the direction it corrects -- an `unbacked_thread` finding built from a record that disowns its own fields, or from flags nothing could read, is no longer raised, so no result is ever newly promoted toward malicious by it. The same validity rule now reaches `--hunt injection` and `--hunt pipe`, which had kept reading the raw `StartAddress` field: an unestablished address no longer produces an `injection.unbacked_thread_startaddress` finding and score, a `pipe.start_address_proximity_lead`, or a pipe unbacked-thread record. `--hunt injection` gains the check id `injection.start_address_not_established` (`findings[].check` is an open string vocabulary, so this is producer behavior within v2.20, not a schema change): an observation carrying how many records were held back, and an explicit limitation that whether those threads begin inside unbacked memory is undeterminable rather than a checked negative. `coverage.status` and the exit code do not move; an injection score whose only start-address evidence was unestablished falls from 1 to 0. `--diff` reads the same derivation for its own `start_address_before`/`start_address_after`. `start_address_state` gains its fourth cause in the same change: dumpex now parses ThreadInfoListStream itself rather than reading DumpFlags from raw bytes while every other field came from the installed library's fixed-layout parse, so a record whose own declared size stops short of the StartAddress field -- or one the stream's DataSize cuts off partway -- reports `absent` instead of the zero the library's empty read produced. Readable DumpFlags never promote such a record to `recorded`, so `start_address_state: "absent"` can now appear alongside `dump_flags_state: "resolved"`, which the schema's own conditionals previously forbade; `recorded` and `unverified` are now also required to carry a non-null `start_address`. A record the stream or the file cuts short mid-way is still delivered for the fields it did carry, so a thread whose record arrived only as far as its ThreadId and DumpFlags keeps both and stays present -- previously it was dropped, which `--diff` reported as a `removed` thread with `COMPLETE` coverage and no stated reason. A whole ThreadId is enough for a record to survive -- it is what attributes a record to a thread at all -- so a record reduced to four bytes keeps its TID, reports its DumpFlags as unreadable rather than as 0, and no longer produces a false `removed` thread in `--diff`. Only a record without even a whole ThreadId is not offered. `--threads`, `--report`, `--diff` and `--hunt injection` gain two `coverageLimitation.code` values for the incompleteness that remains: `THREAD_INFO_STREAM_TRUNCATED` (`affected_count` = declared minus delivered -- that stream cannot settle which TIDs exist) and `THREAD_START_ADDRESS_UNAVAILABLE` (`affected_count` = records that arrived but establish no start address). `--report` and `--hunt injection` additionally report the existing `SOURCE_KEY_MISMATCH` code for a third case they previously missed entirely: a ThreadInfoListStream that is present and complete but does not cover one of the threads the base ThreadListStream lists -- the same per-TID gap `--threads` has always reported, now in the same words from every command. All three move `coverage.status` to `partial` and the exit code from 0 to 3 where such a dump previously reported `complete`/0, and `--hunt injection`'s verdict moves from CLEAN to INCONCLUSIVE. A `--report` card anchored on a thread the stream does fully describe stays `complete`. `--diff` still reports the records it has; what changes is that the added/removed sets no longer present themselves as a closed answer. |

## Producer behavior within v2.20

Not every change to what dumpex emits changes the wire shape. These narrow what
a current document contains without changing what it may contain (`coverageLimitation.code`
and `diagnosticEntry.code` are both intentionally open string vocabularies), so
they need no schema bump and every archived document stays valid — but a
consumer that inferred a rule from earlier output should read them.

- `--report` gains the `coverageLimitation.code` value `REPORT_PE_HEADER_VALIDATION_INCOMPLETE`:
  at least one triage card's structural PE parse over an MZ-prefixed candidate
  could not settle `has_injected_pe` (`region.pe_header_state == "short_read"`
  -- a required header offset fell past what was actually examined). This is
  independent of `REGION_READ_TRUNCATED` (the raw byte count): the two can
  fire together on the same card when the raw read itself was ALSO short, so
  neither code's fixed text names a specific cause -- both stay accurate
  whether the underlying read was full or truncated. `coverage.status` becomes
  `partial` rather than staying `complete` and silently dropping this
  unresolved question; `verdict` is unaffected -- an undetermined fact is
  never inferred as malicious.
- `--extract` gains the `diagnosticEntry.code` value `EXTRACT_INJECTED_PE_DETECTED`,
  fired only when the extracted bytes' MZ header structurally validates in
  full AND the containing region is confirmed unregistered AND MEM_PRIVATE or
  executable -- the same bar `--report`'s `injected_pe` finding uses. A bare
  `MZ` prefix that does not meet that bar keeps the existing
  `EXTRACT_MZ_HEADER_DETECTED` code, whose message no longer claims "this
  looks like an injected PE" for evidence that does not support the claim,
  and now names the SPECIFIC reason (module-backed, no covering MemoryInfo
  region, structurally invalid, a capture-length gap, or a confirmed
  non-private/non-executable mapping) instead of listing every possible
  cause in one sentence.
- `extractRecord` gains `pe_header_state`: the same `ok`/`pe_invalid`/
  `short_read`/`null` vocabulary `reportRegionInfo.pe_header_state` uses, set
  exactly when a structural PE parse was attempted (an MZ header was
  detected AND the extracted address is confirmed unregistered with a
  covering MemoryInfo region) and `null` otherwise.
- `--extract` gains the `coverageLimitation.code` values
  `EXTRACT_MODULE_CONTEXT_UNAVAILABLE` and `EXTRACT_MEMORY_INFO_UNAVAILABLE`:
  when an MZ header is detected, `ModuleListStream` is now consulted to
  decide `EXTRACT_INJECTED_PE_DETECTED` vs. the weaker claim, and it being
  entirely absent lowers `coverage.status` to `partial` (moving the exit
  code from 0 to 3) instead of silently degrading the diagnostic while
  still reporting `complete`. `MemoryInfoListStream` is consulted -- and
  required -- ONLY when module ownership does not already settle the

  type, so a dump missing `MemoryInfoListStream` entirely is not a

  handle stream is absent, or readable with no recorded parse failure.
- When a HandleDataStream parse failure is recorded, `--hunt pipe` scores no
  handle from that stream, and its `details.handle_pipes` is empty even if the
  dump also carried a parsed stream object. A dump can declare the same stream
  type at more than one directory index; only one parse outcome is retained per
  stream type, so which entry a surviving object came from cannot be
  determined. A consumer must therefore not read an empty `handle_pipes` beside
  a `failed` `handle_data` as "no pipe handles were held" — the record's
  `coverage.status` is `partial` and the hunter's own `status` is
  `INCONCLUSIVE`, never a clean result. `--handles` resolves the same dump the
  same way.

## Important upgrade boundaries

### v2.12 to v2.13

Consumers must recognize `result.kind` values `process`, `handles`, and
`profile`. The older `pid` and `peb` kinds are not aliases and are not produced.
The CLI likewise uses `--process`, `--handles`, and `--profile`.

### v2.8 to v2.12

Coverage gaps became actionable rather than count-only:

- v2.8 identifies skipped targets;
- v2.9 groups them into the hunt-all investigation queue;
- v2.10 records bounded deep-triage content signals;
- v2.11 identifies hidden-PE candidates precisely;
- v2.12 distinguishes skip causes, capture completeness, and budget facts.

Consumers should use structured limitation/action fields rather than parsing
`coverage.reasons` text.

Deep-mode triage is a historical v2.10-v2.13 producer shape. Current dumpex
keeps those schemas frozen for archived output validation but emits metadata-
only investigation actions; `--triage-skipped` is temporarily unavailable.

### v2.4 to v2.7

The hunt result joined the v2 envelope in v2.4. Later versions expanded the
normalized finding shape and changed Cobalt Strike config field representation.
Parsers that ingest hunt details must validate the claimed schema version before
assuming field keys or raw-value availability.

### v2.0 to v2.3

The earliest v2 releases added comparison, extraction/string, and report result
kinds incrementally. A parser should dispatch on `result.kind` and must not
assume a record kind existed in every historical v2 file.

## Legacy v1.1

[`dumpex-output-v1.1.schema.json`](../../dumpex/schemas/dumpex-output-v1.1.schema.json)
is retained for archived hunt output created before the v2.4 migration. No
current command produces v1.1. Its root shape is different from v2 and should be
handled as a separate contract, not coerced into the current envelope.

## Upgrade checklist

1. Read `meta.schema_version` before parsing `result`.
2. Validate with the matching packaged schema.
3. Dispatch on `result.kind`.
4. Preserve unknown historical documents rather than rewriting them in place.
5. Update stored fixtures and downstream mappings deliberately for breaking
   field changes.
6. Keep the evidence hash and original JSON together during migration testing.
